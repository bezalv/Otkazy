# Поиск переходов в отказ

`discoverTransitions({ client, compareOutcomes, from, to, cursor, maxPages,
pageDelayMs, wait })` читает часть истории стадий через внедрённый
`client.request('crm.stagehistory.list', body)`. Функция ничего не записывает,
не ставит сделки в очередь и не меняет курсор в хранилище.

`from` и `to` — строки ISO 8601 с часовым поясом. Интервал включает начало и
исключает конец. Запрос использует `entityTypeId: 2`, сортировку `ID ASC`,
`start` и возвращаемый Битриксом `next`. На стороне приложения выбираются
только события `STAGE_ID === 'C23:LOSE'` внутри интервала. Для каждого перехода
формируется ключ `bitrix24:deal-stage-history:<ID истории>`; повторные переходы
одной сделки имеют разные ключи. Серверные фильтры по времени и стадии здесь
не применяются, потому что их сочетание для этого метода на нашем портале ещё
не подтверждено. Это может потребовать большого числа запросов.

На один вызов допускается от 1 до 100 страниц, по умолчанию 10. Между запросами
разных страниц — 1000 мс. Повторяемая ошибка запроса получает до трёх попыток
с паузами 2 и 4 секунды. Сортировка, обязательные поля, число строк, `next` и
`total` проверяются; некорректный или неполный ответ прерывает вызов ошибкой.
Персональные данные и тексты внешних ошибок в исключения не включаются.

`compareOutcomes(events)` — обязательный асинхронный адаптер чтения сохранённых
исходов. Для каждого переданного события он возвращает ровно один объект с
`event_key` и `status`. Для `processed`, `skipped_by_reason`, `waiting_audio`,
`pipeline_error` необходимо `evidence`: либо `event_key` самого сохранённого
исхода, либо `deal_id` и `lose_date`, совпадающие со сделкой и временем события.
`not_found` допускается как `unprocessed` только при `complete: true`: адаптер
тем самым утверждает, что проверил все соответствующие источники. `unknown`,
неподтверждённый отрицательный результат и несовпадающие доказательства дают
`unverified`. Ошибка адаптера или отсутствующий результат прерывают весь вызов.
Реального адаптера к Supabase здесь пока нет.

Результат содержит `events` с `disposition` (`already_handled`,
`already_waiting`, `retry_needed`, `unprocessed`, `unverified`), число
`pages_read`, `scan_complete` и `next_cursor`. `next_cursor` можно передать
следующему вызову с тем же окном. Вызывающий код должен сохранять продолжение
атомарно с постановкой найденных событий в устойчивую очередь. Если этого
механизма нет, безопаснее повторно прочитать страницу и дедуплицировать по
`event_key`, чем отдельно сохранять курсор. При постановке задания дата
перехода должна передаваться как ожидаемая дата отказа, а перед обработкой
должна сверяться с текущей историей сделки. При повторном переходе старое
событие не должно приводить к повторному анализу нового отказа.

`scan_complete` сообщает, что текущий последовательный обход страниц дошёл до
конца. **Он не подтверждает полноту исторического периода.** Документация не
обещает снимок данных на время offset-пагинации. При одновременном изменении
истории строки могут сместиться между запросами. Поэтому `coverage_guaranteed`
всегда `false`. Необходимы дополнительная сверка способа получения согласованной
выборки, стратегия повторного обхода с перекрытием и проверка на портале до
использования этого сканера как единственного источника всех пропущенных сделок.
Задержка ограничивает только один вызов сканера, для параллельных процессов
нужен общий ограничитель запросов к Битриксу.

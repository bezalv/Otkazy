# Транскрибация звонков

`transcribeCalls({ dealData, transcribe })` последовательно обрабатывает
коммуникации с `type: 'call'` и признаком `_needs_transcription`. Источник —
ноды «Config + Фильтр звонков», «Транскрибировать все звонки» и «Собрать итог»
из локальной выгрузки 19.10. Входная сделка и её коммуникации не изменяются.

Внедряемый `transcribe` вызывается с объектом `{ deal_id, file_id, activity_id,
call_date, call_direction, comm_index, channel_count, speaker_role? }` и
возвращает результат подворкфлоу с `success`, `formatted_dialog`, `manager_text`,
`client_text`, `conversation`, `total_replicas`, `transcript_engine`, а при
сбое — `error`, `retryable`, `channels_mismatch`. Адаптер обязан разрешить
`file_id` через `disk.file.get`, проверить скачивание и вызвать распознавание.
Сетевая ошибка передаётся исключением. Сам модуль сети не касается.

Сначала выполняется стерео-проход. При пустом успешном диалоге либо отказе по
числу каналов вызывается моно-проход с ролью «Говорящий». Моно с пустым текстом
считается пустой успешной записью. Ошибки собираются в `transcription_errors`
и `transcription_stats.errors` с длительностью звонка для `pipeline-gate`.
Все ошибки звонков имеют `technical_failure: true`. Флаг `retryable` отдельно
сохраняет признак повторяемости, возвращённый сервисом. Шлюз полноты должен
блокировать технический сбой независимо от этого признака.
Адреса и токены из ошибок удаляются. Результат всегда имеет
`ready_for_analysis: false`: вызывающая сторона обязана проверить `voice_failures`,
ошибки звонков, скриншоты и полноту данных до вызова судьи.

Помимо старого `full_data`, ответ содержит объединённые `communications` и
`transcription_stats`. Исходные метаданные сделки остаются в `full_data`.
Транскрипты встраиваются по `activity_id`; нераспознанные и непустые исходные
коммуникации не удаляются. Модуль не кэширует результаты. В исследованной ноде
повторно запускалось распознавание всех звонков, готового кэша по ID там не найдено.

Консервативные отличия от архивной ноды: отсутствие URL, `fileId`, ID звонка,
несовпадение ID в ответе и повторяющиеся ID дают блокирующую техническую ошибку.
Строка с URL в `_needs_transcription` тоже считается признаком записи: именно
её может вернуть сборщик, когда `SETTINGS.RECORD_URL` заполнен. Для старой
коммуникации без флага наличие URL запускает обработку, а явное `false`
сохраняется. Фактический
признак моно в ответе или метка «Говорящий:» сохраняются как `mono` даже если
стерео-запрос вернул непустой текст. Это предотвращает ложное разделение ролей.

Нужно ещё проверить интеграцию настоящего адаптера транскрибации, скачивания и
хранилища; модуль не подменяет их. Проверки: `node --test tests/restore-calls/run.mjs`.

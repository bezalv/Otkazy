# Сохранение результата

`persistResult(pool, result)` использует отдельную сессию пула PostgreSQL и
записывает изменения одной сделки в одной транзакции. Поля `operation_id` и
`lease_token` обязательны. `operation_id` совпадает с `lost_processing_jobs.id`.
Вначале блокируется строка задания и проверяется аренда, затем проверяется
наличие анализа с тем же `pipeline_operation_id`. Дата отказа карточки и
очереди аудио сверяется с датой задания.

Для `processed` с `silent=false` сохранённый результат остаётся в состоянии
`processing`. Функция возвращает `needsExternalActions: true`, потому что запись
комментария и уведомлений ещё не выполнена. Для тихого разбора, технического
сбоя, пропуска и постановки ожидания аудио задание закрывается транзакционно.
`silent` и `screenshots` берутся из строки задания.

После повторного захвата до сбора данных и вызова модели вызывающая сторона
должна выполнить `loadResumableResult(pool, { operation_id, lease_token })`.
Если анализ уже сохранён, функция возвращает поля для продолжения внешних
действий, а модель повторно вызывать не нужно. Право на отправку и состояние
доставки эта функция не устанавливает.

`COMMIT_OUTCOME_UNKNOWN` означает, что клиент не знает, завершился ли коммит.
Исключение содержит `operationId`. Автоматического повтора записи нет.
`lookupOperation(pool, operationId)` отдельно читает состояние задания и анализа.
Если результат ещё не виден, нужно учитывать возможность незавершённого коммита.

## Проверки и ограничения

Миграция очереди `20261105052525_lost_processing_jobs.sql` необходима для этих
запросов. В действующей базе на момент написания она не применена. Фикстура
`tests/restore-persistence/synthetic-schema.sql` содержит только определения
таблиц из `information_schema`, без клиентских данных.

`node --test tests/restore-persistence/*.test.mjs` запускает моки и, если в
`tmp/pgtest` установлен PGlite, изолированный PostgreSQL в памяти. Этот тест
проверяет SQL, сохранение, откат и состояние очередей на одной сессии. Конкуренцию
независимых соединений и реальные сбои сети нужно проверить отдельно на тестовом
PostgreSQL. Без сохранённого статуса отправки комментария и уведомлений внешние
действия нельзя безопасно повторять после неизвестного ответа Bitrix24.

# Отчёт о ручной сверке

`node app/src/operator/triage.mjs` читает `DATABASE_URL` из окружения и выводит
только суммарное число заданий `needs_review` по состояниям комментария и
уведомления. Он не запускает приложение, обработку сделок или внешнюю отправку.
В БД используется транзакция только для чтения; при действующем RLS и отсутствии
таблицы отчёт завершается ошибкой, а не сообщает ложный ноль. Подключение требует
проверяемый TLS-сертификат и сессионный порт Supabase 5432.

Проверку не запускать до применения новых миграций в согласованном окружении.
Отчёт не показывает сделки или пользователей, не снимает блокировку и не
восстанавливает доставку. Нужна отдельная процедура сверки конкретного случая:
у комментария совпавший хеш полезен для поиска, но отсутствие совпадения не
доказывает, что Битрикс не принял его. Повтор без сверки может продублировать
уведомление или комментарий.

`summarizeDiscovery(report)` в `report.mjs` удаляет идентификаторы и показывает
суммы уже полученного отчёта `discoverTransitions`. Окончание просмотра страниц
не означает гарантию полноты; функция всегда возвращает `coverage_guaranteed: false`.
Ни эта функция, ни команда не ставят задания в очередь. Интерфейс и безопасная
процедура точечного запуска пропущенных сделок пока не реализованы.

`backfill.mjs` помогает подготовить **неисполняемый** список для ручной работы.
`listUnprocessedHistoryIds(report)` возвращает только технические ID переходов,
а `reviewSelectedBackfill` принимает явный непустой выбор этих ID, повторно
сверяет исходы и через существующий `readCurrentTransition` проверяет текущий
первую строку истории сделки при текущей стадии отказа. Если история, стадия или
исход изменились, элемент получает отдельную причину. `first_history_row_matches`
означает только совпадение с первой строкой ответа, а не доказанно последний
переход: метод сортирует по времени и порядок при одинаковых отметках не проверен.
Результат всегда содержит `can_enqueue: false`. Функции не пишут
в базу, не запускают очередь и сами ничего не выводят в stdout. Библиотека не
даёт гарантии полноты истории и не подтверждает, что отчёт принадлежит именно
подключённому порталу.

Перед реализацией реального запуска надо отдельно решить и проверить контракт:

- Привязать сохранённый отчёт, подтверждённый список ID и свежую проверку к одному
  порталу; сохранить состав и параметры одобренного запуска от подмены и повтора.
- Согласовать дедупликацию live/backfill: оба используют один ключ перехода,
  но существующий `enqueue` считает различия `trigger_type` или `silent`
  конфликтом. Нельзя молча менять параметры уже существующего задания. Для
  тихого и обычного запуска нужны явные правила при одновременном live-событии.
- Совместить последнюю проверку БД и постановку задачи в одной транзакции с
  понятной блокировкой, которую соблюдают все участвующие обработчики. Старый
  n8n этот контракт не соблюдает: его нужно остановить или обеспечить совместимость.
- Признать, что Битрикс и PostgreSQL не образуют общей транзакции: стадия может
  измениться после проверки. При выполнении обязательно повторно проверять
  актуальный переход, разрешить неоднозначность одинаковых временных отметок
  в истории и безопасно завершать устаревшие задания. Нужны тесты на
  двух настоящих подключениях PostgreSQL и конкурирующее live-событие.
- Отдельно решить, что делать со статусами `unknown`, `retry_needed`, уже
  существующими историческими анализами и неоднозначными результатами COMMIT.
  Их нельзя автоматически считать пропусками или повторять отправки.

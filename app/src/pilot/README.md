# Ручная проверка «Отказов» по историческим разборам

Пилот запускается **только вручную** для явно выбранных от одной до пяти сделок.
Он вызывает `processDeal` напрямую с `silent: true` и не создаёт очередь,
воркер, сервер основного приложения или модуль доставки. В Битрикс доступны
только девять явно перечисленных методов чтения; попытка вызвать другой метод
блокируется до сети. Комментарии, уведомления и данные Supabase не записываются.

Эталоны и конфигурация ожидания аудио читаются в одной транзакции PostgreSQL
`REPEATABLE READ READ ONLY`; затем соединение закрывается до обработки. Значения
секретов, тексты сделок и факты не выводятся в консоль: команда возвращает только
суммы статусов и сравнений. Диагностика использует только фиксированные категории,
названия методов чтения, категории источников и HTTP-код 400–599; текст ошибок,
ответы API и идентификаторы коммуникаций не выводятся. Сам вызывающий код обязан сохранять конфиденциальность
эталонов; адаптеры для тестов являются доверенным кодом, это не песочница для
сторонних JavaScript-функций.

Для реального сравнения потребуются `DATABASE_URL` (сессионный pooler Supabase,
TLS и порт 5432), `BITRIX_REST_BASE`, `POLZA_API_KEY` в окружении, локальный
Node.js 24 и установленные npm-зависимости, включая ffmpeg/ffprobe. Секреты в
аргументы, Git и журнал не помещать. Файл `.env` проекта может не содержать
готовый `DATABASE_URL` или `BITRIX_REST_BASE`: их должен безопасно подготовить
оператор из доступных настроек, не печатая значения.

```text
node --env-file=.env app/src/pilot/command.mjs ID_СДЕЛКИ_1 ID_СДЕЛКИ_2
```

Пример показывает формат, а не готовую команду: нужны реальные явно выбранные
числовые ID и все три переменные окружения. Если источник, исход ожидания аудио
или эталон не подтверждён, результат не объявляется успешным; при технической
ошибке последующие выбранные сделки автоматически не запускаются. Для аудио
локально и временно запускается **отдельный STT-процесс** на loopback; после
завершения он штатно закрывается. Распознавание через Polza/GigaAM и запросы
судьи/писателя в Polza платные и передают провайдеру данные выбранных сделок,
как и действующая методология. При аварийной остановке временные аудиофайлы
могут потребовать отдельной проверки.

Вердикт и класс причины сравниваются отдельно. Точное сравнение фактов учитывает
их структуру, текст и порядок; различие не всегда означает ошибку: текущая
сделка, коммуникации и файлы могли измениться после старого анализа, а ответы
LLM недетерминированы. Одинаковый вердикт тоже не доказывает сохранение всей
методологии. Исторический ID перехода в прежних анализах не подтверждён;
отсутствие ID новой операции само по себе не доказывает, что эталон получен в n8n.

`saved-facts.mjs` — отдельный частичный сценарий: текущие порог данных, судья и
писатель получают уже сохранённый пакет фактов. При явном подключении клиента
Polza он делает платные запросы; при тестировании допускается только мок клиента.
Этот сценарий **не проверяет** сбор Битрикса, транскрибацию, обработку файлов и
формирование фактов. Доступные `bench/data/inputs` и `golden` — историческая
выборка v2.5/Opus, не эталон полного текущего конвейера v2.8/Sol.

Проверка `tests/restore-pilot/saved-parser-fixtures.test.mjs` при наличии этих
локальных файлов проверяет текущий парсер и валидацию ссылок на прежних ответах
без сети, печатая только общее число пакетов и ошибок. Если файлов нет, тест
пропускается. Эти материалы содержат клиентские данные и не добавляются в Git.

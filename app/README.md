# Локальное восстановление «Отказов»

Это незавершённое приложение. `npm start` пока запускает только диагностические
`/health` и `/ready`; обработка сделок и расписания не включаются. Не размещать
его вместо существующего приложения и не применять миграции к рабочей БД до
интеграционных проверок из [плана](../tasks/2026-11-05-vosstanovlenie-bez-n8n.md).

`npm ci` устанавливает Node-зависимости. `ffmpeg-static` и
`@derhuerst/ffprobe-static` скачивают платформенные бинарники при установке;
выполнять её внутри целевой Linux-среды, не копировать `node_modules` из Windows.
`npm run check-runtime` проверяет Node и запускаемость обоих бинарников, но не
подтверждает готовность системы к обработке. В галактике собственный Dockerfile
игнорируется; приведённый здесь образ предназначен только для локальной проверки.
В целевом окружении также требуется `TZ=UTC`: часть исторических дат не содержит
явного часового пояса.
При настройке Gateway необходимо отдельно проверить назначение health-check:
сбой распознавания должен отображаться как неготовность обработчика, но не должен
мешать работающему HTTP-приёмнику сохранять новые события в базу.

Промпты в `prompts/` собираются из проектного источника командой
`node bench/build-restore-prompts.mjs` из корня репозитория и проверяются той же
командой с `--check`. Правки вносить в `prototype/prompts`, а не в копии.

Для будущего запуска потребуются доступы к PostgreSQL проекта, входящий REST-вебхук
Битрикса и ключ Polza. При прямом приёме событий потребуется **отдельный токен
исходящего** вебхука Битрикса и настройки идентификации портала; его нельзя
подменять токеном входящего REST-вебхука. Значения не помещать в Git, журналы или
примеры. Получение и установка токена событий, подключение маршрута, разрешение
доступа Gateway и регистрация события в портале пока не выполнены.
Публичный корневой CA Supabase находится в `certs/` и сверяется перед активным
запуском. Для Supabase pooler требуется сессионный порт 5432; через него
защищённое подключение и установка таймаутов проверены только чтением.

Перед развёртыванием нужно также проверить placement и свободную память именно
нужной галактики, работу индивидуального режима `ALWAYS`, наличие бинарников и
установку npm-зависимостей внутри неё. Все приложения галактики делят ресурсы
одного хоста; двухшаговое создание позволяет проверить выбранную платформой
галактику до загрузки кода, но уже создаёт слот. Старый n8n и новый обработчик
не должны одновременно выполнять одни и те же задачи.

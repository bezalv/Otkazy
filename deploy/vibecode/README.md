# Подготовка «Отказов» к отдельному развёртыванию в Вайбкоде

Эти материалы — пример для будущего запуска. Они не создают приложение, не
меняют настройки галактики и не применяют миграции. Не загружать код в слот
существующего приложения. Примеры содержат только режим `setup`: обработчик
сделок и расписания в нём не запускаются.

## Что нужно от владельца

- Подтвердить способ разместить **отдельное** приложение именно в существующей
  галактике `galaxy-mvkhypw07b1e`. При обычном создании платформа сама выбирает
  хост; параметра с нужной галактикой в публичном API не описано. Создание пустого
  слота уже может привести к созданию другого платного хоста. В кабинете есть
  восстановление готовой резервной копии с выбором галактики, но применимость
  для нового приложения, запуск копии и стоимость этого пути не проверены.
  Если вопрос нельзя решить в доступном интерфейсе, понадобится уточнение
  администратора портала или поддержки Вайбкода.
- Доступ администратора Битрикс24 для подключения события `ONCRMDEALUPDATE`.
  Для прямого исходящего вебхука понадобится его токен события и `member_id`;
  если настройку нельзя выполнить доступными правами, владелец создаёт вебхук
  после получения адреса нового приложения и передаёт значения через защищённое
  хранилище приложения или локальный `.env`, а не в чат. Прежний входящий
  REST-вебхук уже доступен; пользователь не просил его менять.
- Перед включением убедиться, что старый n8n не обрабатывает эти же сделки и
  его запущенные обработки завершены: его блокировки не согласованы с новой
  очередью. Определить ответственного за разбор `needs_review` и проверить,
  что приняты меры по резервному копированию данных.
- Для прямой доставки событий может понадобиться действие владельца в кабинете
  по подтверждению публичного доступа. На защищённом портале платформа может
  отдельно вернуть `AUDIENCE_APPROVAL_REQUIRED`.

Пароль Supabase и ключ Polza уже обнаружены в локальных настройках; не просить
их повторно без необходимости. Яндекс SpeechKit не используется. Секреты не
попадают в JSON-примеры, архив, Git, журнал или отчёт.

## Порядок безопасной подготовки и проверки

1. Получить идентификатор целевой галактики и проверить его связь с именем в
   кабинете. Проверить доступные память/CPU, сборку и наличие места для нового
   процесса. `GET /v1/me` даёт предварительные сведения; окончательный выбор
   места осуществляется при создании. Ни один описанный метод не гарантирует
   заранее, что новый слот окажется на указанном хосте.
2. Подготовить исходники только после завершения проверки кода. В корне архива
   должны находиться `package.json`, `package-lock.json`, каталоги `src/`,
   `prompts/` и `certs/` из `app/`. Не включать `node_modules`, `.env`, `tmp/`,
   журналы и локальные бинарники Windows. Перед отправкой проверить состав
   архива и отсутствие секретов. Формат — `tar.gz`, в API передаётся его
   содержимое в base64, а не путь к файлу. Пакеты ffmpeg скачивают бинарники при
   `npm ci`; понадобится доступ сборки к соответствующим ресурсам.
3. Когда адресное размещение и расходы согласованы, создать отдельный пустой
   слот через `POST /v1/infra/servers`, используя структуру
   [create.example.json](create.example.json). Это действие уже создаёт ресурс.
   Сразу проверить `kind = GALAXY_APP`, UUID `galaxyId` целевой галактики,
   `reused` и `next`. При `reused = true`, другом хосте, неизвестном UUID или
   любом неопределённом результате код не загружать и чужой слот не менять.
   Слот без кода примерно через 20 минут может перейти в состояние ошибки.
4. Только для нового проверенного слота выполнить
   `POST /v1/infra/servers/{id}/deploy` по
   [deploy.setup.example.json](deploy.setup.example.json), подставив архив в
   `source.content`. Это описание формы, не готовый запрос: строка-заглушка не
   является архивом. `healthPath` должен быть `/health`, поскольку `/` возвращает
   404. В `setup` `/health` сообщает, что процесс работает, а `/ready` остаётся
   неготовым; это ожидаемо и не доказывает готовность анализа.
5. Проверить журнал сборки, запуск ffmpeg/ffprobe в Linux, режим приложения
   `ALWAYS`, доступность health-check и влияние на память/CPU общих приложений.
   Пользовательский Dockerfile и `preStart` для Galaxy не выполняются. Сборка
   ограничена половиной памяти хоста. `ALWAYS` относится к новому приложению и
   может удерживать галактику активной с полной тарификацией.
6. До применения миграций и активации отдельно закончить проверки из
   [плана восстановления](../../tasks/2026-11-05-vosstanovlenie-bez-n8n.md):
   конкурентные транзакции на изолированной БД, выборочный тихий пилот в
   тестовом контуре,
   совместимость потребителей, точную идентификацию пропусков и процедуру
   сверки неопределённой доставки. Настройку `lost_live_config.enabled_at`
   нельзя случайно менять или удалять: она фиксируется один раз и должна
   совпасть с `LIVE_ENABLED_AT` в окружении приложения.
7. Только после этих проверок настроить доставку событий, передать полный набор
   переменных и включить обработку. Пользовательские `env` необходимо заново
   передавать при каждом deploy; значения секретов из кабинета имеют приоритет
   над одноимёнными `env`. Изменение секретов может пересоздать контейнер.
   Для активного режима необходимы `OTKAZY_MODE=active`, `TZ=UTC`,
   `DATABASE_URL`, `BITRIX_REST_BASE`, `BITRIX_DOMAIN`, `BITRIX_EVENT_TOKEN`,
   `BITRIX_MEMBER_ID`, `LIVE_ENABLED_AT` и `POLZA_API_KEY`. Порт предоставляется
   платформой. `DATABASE_URL` для Supabase pooler должен использовать сессионный
   порт 5432 и TLS. Параметры проверяются при старте `app/src/main.mjs`.

Не запускать пропущенные сделки по предварительной выборке автоматически:
отчёт backfill пока не является исполняемым и не подтверждает полноту истории.

## Доставка событий

- **Прямой исходящий вебхук.** Для `/webhooks/bitrix` нужен внешний доступ;
  переключение `accessPolicy` на `PUBLIC` относится ко всему субдомену
  приложения, а не к одному маршруту. Действующий обработчик проверяет токен и
  сведения портала. До активации нужен согласованный способ включения доступа и
  регистрации события: при ошибке доставки обычный исходящий вебхук не следует
  считать надёжной очередью.
- **Black Hole.** Вайбкод документирует доставку событий с повторами без
  публичного URL, но требует сервер, привязанный к авторизованному
  OAuth-приложению с ключом `vibe_app_`; личного `vibe_api_` недостаточно.
  Наличие и настройки такого приложения для «Отказов» не подтверждены. Перед
  выбором этого пути надо отдельно проверить совместимость доставки и
  аутентификации с обработчиком.

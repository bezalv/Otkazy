# Сделка 127888: почему ожидание аудио заняло сутки

Проверка 25.11.2026: код приложения, Supabase и текущие CRM-дела Б24. Изменений в приложении, портале и рабочей базе не вносилось; платные модели не вызывались. Время ниже — Новосибирск (UTC+7).

## Подтверждённая причина остановки

`lost_audio_wait` хранит только один ожидаемый звонок: CRM-дело **1697414**. Его начало — 19.11 13:58:44, конец — 13:58:48 (4 секунды), `PROVIDER_ID=VOXIMPLANT_CALL`, `COMPLETED=Y`, файла и `SETTINGS.RECORD_URL` нет. `COMPLETED=Y` означает завершённое CRM-дело, само по себе это не доказывает состоявшийся разговор или ожидаемую запись.

Отказ — 20.11 13:50:06; первое обнаружение отсутствия файла — 13:55:25.032. Дедлайн — 21.11 13:55:25.032, строго через 24 часа после первой проверки. Было 13 проверок. Анализ 2263 сохранён 21.11 в 13:55:43, уведомление доставлено только пользователю 65 в 13:55:46.348. Комментарий в CRM пропущен. Судья не вызывался: `judge_model=none (audio-wait gate)`, `data_scope=not_collected`.

Текущий API-ответ на отбор рабочего сборщика содержит пять CRM-дел:

| CRM-дело | Длительность | Файл | Кандидат на ожидание при отказе |
|---|---:|---|---|
| 1690458 | 0 сек | нет | нет |
| 1690466 | 0 сек | нет, MISSED_CALL=true | нет |
| 1690504 | 35 сек | 1710660 | нет: звонок старше суток |
| 1697414 | 4 сек | нет | да — единственный блокирующий |
| 1697424 | 28 сек | 1715076 | да, но запись доступна |

Вызов действующей `awAssess` на свежем ответе с сохранённым временем первой проверки воспроизводит `waiting`, `pending_calls=["1697414"]`. Это совпадает с исторической строкой Supabase. Текущая проверка доступности аудио (`awHasAudio`) видит файлы 35- и 28-секундных разговоров через `FILES[*].url`.

## Что подтвердилось и что не подтвердилось в гипотезах

- **Суточный таймер:** подтверждён. Срок считается от первого обнаружения отсутствия записи, а не от времени звонка, загрузки файла или ровно от перехода в отказ.
- **Проверка только прямого URL:** не является причиной этого случая. `awHasAudio` и нормализатор уже читают `FILES`. Статистика `CALL_RECORD_URL` рабочим сборщиком не используется.
- **Пропуск исходного лида:** подтверждён отдельный пробел. Сборщик вызывает `crm.activity.list` с `OWNER_TYPE_ID=2, OWNER_ID=127888`; звонок 1689734 принадлежит лиду 320282 и отсутствует в полученных пяти делах. Прямое чтение 1689734 возвращает файл 1710338 и длительность 213 секунд. Дополнительные привязки, указанные в исследовании пользователя, в этой проверке отдельно не запрашивались.
- **Порог 60 секунд:** это правило достаточности данных в промпте судьи, с исключением при прямом отказе клиента. Оно не отфильтровывает короткие звонки из сбора и не вызвало данное ожидание.
- **Доставка Билайн → Б24:** указанные пользователем задержки файлов — отдельная проблема. В ходе этой проверки сделки 126092/120419 и сторона АТС повторно не исследовались.

## Ограничение проверки

`voximplant.statistic.get` вернул HTTP 401 `insufficient_scope` для используемого вебхука. Поэтому результат соединения четырёхсекундного звонка не подтверждён: нельзя утверждать, что это недозвон, сброс или состоявшийся разговор без записи. Сам факт длительности 4 секунды не доказывает отсутствие содержания.

## Требуемое исправление

1. Различать состоявшийся разговор с ожидаемой записью и техническую/неуспешную попытку. Не использовать только положительную длительность и `COMPLETED=Y` как основание заблокировать весь анализ на сутки. Не вводить общий запрет на звонки короче 60 секунд.
2. Собирать активности с подтверждённой привязкой к сделке, включая исходный лид; исключать чужие сделки того же контакта, дедуплицировать по ID активности и сохранять временную отсечку по отказу.
3. Уточнить сообщение таймера: перечислять ID ожидаемых звонков, длительности, найденные файлы и способ проверки. Формулировка «запись не появилась» не должна представлять предположение о доставке как установленный факт.
4. Сохранять снимок отбора и причины ожидания до раннего выхода `audio-wait`. Сейчас постоянные `lost_prejudge_artifacts` создаются после него; у сделки 127888 таких артефактов нет. Историческую причину удалось восстановить по `observations`, очереди и текущим CRM-данным.
5. После исправления повторить 127888 и остальные истёкшие ожидания с прежними ограничениями пилота: только получатель 65, без записей в карточки.

## Исправление по поручению пользователя

- Для завершённого события до 5 секунд без файла блокирующее ожидание снято. Порог выбран консервативно для ожидания, он не доказывает отсутствие разговора; факт остаётся системным с неизвестным содержанием. Явно пропущенный звонок также не требует записи. Доступное аудио любой длины по-прежнему распознаётся, ID файла без ссылки и исчезнувшая ранее доступная запись не обходят ожидание.
- Добавлен сбор активностей исходного `LEAD_ID` с проверкой `crm.activity.binding.list`: включается только явная привязка к текущей сделке. Повторы ID исключаются, временная отсечка сохраняется; ошибка проверки блокирует неполный сбор.
- При истечении ожидания сообщение содержит ID CRM-дел и длительности, прямо объясняет, что сутки — срок ожидания приложения. В observations записываются время проверки, длительность и ID известных файлов.
- Проверка Б24 в режиме только чтения: звонок 1689734 привязан к лиду 320282, сделке 127888 и контакту 163770. Новый сбор возвращает 6 событий, из них 3 с записями (213, 35, 28 секунд). Ручной повтор прежней истёкшей очереди получает `action=analyze`.
- Все 556 тестов завершились успешно. Деплой и полный повтор выполнены после тестов; получатель остался 65, комментарии в CRM отключены.

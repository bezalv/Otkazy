Проверка выполнена только чтением API существующего ключа; платных запросов и изменений настроек не было. Пользователь разрешил использовать существующий ключ, общий предел тестов — 500 ₽. Ключ общий и не имеет подтверждённого серверного лимита.

На момент сверки lifetime usage составлял 3363,55071086 ₽ при исходном значении 3361,06059107 ₽: прирост общего ключа — **2,49011979 ₽**. Два последовательных чтения совпали. История с 08.11 09:00 до 09.11 01:20 UTC содержала 170 записей: 168 завершённых GigaAM, одну неудачную GigaAM и одну неудачную Aiesa. Обе неудачные записи имели цену 0 ₽; сумма всех 170 совпала с приростом usage. В видимом фильтре pending запросов нет, резерв поставщика равен нулю. Доступ к кабинету `polza.ai` напрямую давал таймаут; документированный API-хост `api.polza.ai` отвечает на те же GET `/api/v1/key`, `/api/v2/balance` и `/api/v1/history/generations`.

## Сверка серии из 160 вызовов

В локальном журнале предыдущего прогона 127078 есть 160 последовательных пар состояний «до/после» и отдельные резервы по 2 ₽. За интервал жизни журнала история Polza содержит ровно 160 завершённых генераций GigaAM/STT. Для **каждой из 160** их стоимость совпала до восьмого десятичного знака с изменением lifetime usage соответствующей пары, а переходы usage между соседними парами непрерывны. Последующее чтение usage на следующий день осталось тем же. Это сильное основание снять консервативный локальный резерв **320 ₽**, не путая его с фактически списанными средствами.

Прямого идентификатора generation в синхронных ответах GigaAM журнал не получил. Поэтому сопоставление по времени, порядку и индивидуальным суммам не является математическим доказательством идентичности запросов; общий ключ также может использоваться другими клиентами. Пустые ответы 22 фрагментов эта сверка не объясняет и не превращает в тишину. Продолжение допускается только с контролем свежих значений и немедленной остановкой при постороннем списании или неполной истории.

## Осторожная ёмкость

Резервы предыдущих неопределённых попыток **108 ₽**, неудачной Aiesa **20 ₽** и случайного запуска локального теста **20 ₽** сохраняются, всего **148 ₽**. При наблюдаемом приросте 2,49011979 ₽ и после снятия только сопоставленных 320 ₽ расчётная осторожная ёмкость составляет **349,50988021 ₽**. По временам остальные старые попытки также согласуются с девятью предыдущими записями истории, а Aiesa — с одной последующей неудачной записью, но идентификаторы всех исходных попыток не зафиксированы; это не основание автоматически освобождать оставшиеся резервы.

При прежнем локальном резерве 2 ₽ на физический STT POST в эту ёмкость помещаются не более **174 запросов** без судьи и писателя. Если предварительно удержать по 60 ₽ на один вызов каждого из них, остаётся не более **114 STT POST**. Это лишь арифметика локальных резервов: точный верхний предел счета не гарантирован поставщиком, а иные расходы общего ключа уменьшают остаток. Имеющийся runner принудительно ограничен 160 фрагментами; один новый полный прогон 215 фрагментов без промежуточного урегулирования при этих допущениях не помещается. Результаты необходимо безопасно сохранять локально по мере готовности, чтобы перезапуск не требовал оплачивать те же фрагменты заново; рабочая БД для контрольного прогона не изменяется.

Опубликованный каталог моделей на момент чтения указывал GigaAM 0,24555 ₽/мин и Aiesa 0,1704 ₽/мин. Для двух каналов Aiesa продолжительностью около 9,49 мин каждый пропорциональная оценка — около 3,24 ₽; правило округления и фактический провайдер необходимо проверять, поэтому это не гарантия цены. При резерве 20 ₽ на каждый из двух физических POST и сохранении 148 ₽ старого резерва общий расчётный верх локальных резервов с текущим расходом — 190,49011979 ₽. Если первый запрос не завершён или сервис недоступен, второй не отправляется автоматически.

## Требования к следующему runner

1. Использовать существующий ключ из окружения без вывода или записи секрета, официальный API-хост и только конкретные разрешённые источники. Перед началом и каждым платным вызовом читать свежий usage, баланс и видимую историю pending; межпроцессный lock защищает лишь процессы, использующие этот же протокол.
2. До физического POST записывать и синхронизировать журнал с резервом и проверкой общего лимита 500 ₽. Запрещать автоматические повторы, редиректы и параллельные платные POST; ограничивать длительность/объём аудио и запросы модели.
3. После ответа сверять новое usage с единственной подходящей завершённой записью истории, моделью, интервалом времени и стоимостью. Если история запаздывает, появился посторонний расход, платёж неизвестен, результат прерван или данные противоречат друг другу — сохранять резерв и прекращать новые платные вызовы. Отсутствие generation ID и независимого контроля других потребителей ключа остаётся ограничением даже при совпадении сумм.
4. Сохранять защищённый локальный checkpoint завершённых фрагментов и их привязку к конкретному исходному файлу и параметрам, чтобы возобновить проверку без повторной оплаты. При расхождении входов — не смешивать результаты. Комментарии, уведомления, автоматическую обработку и запись результатов в рабочую БД не включать.

# Поиск надёжного автора в переписках Wazzup и Wappi

## Результат проверки

Только чтением проверены сообщения по шести заранее выбранным сделкам. По пяти получены структурные результаты; шестая, 118413, вернула `unverified`, и причину по этой диагностике установить нельзя. История дополнительных запросов ограничена последней страницей и не доказывает полноту более старых сообщений.

В сделке 127114 история Wazzup содержала 26 сообщений. У 22 есть непустой внешний идентификатор `params.connectorMid`, каждый из этих 22 идентификаторов в проверенной сессии различен. Шесть сообщений имеют наблюдаемый исходящий заголовок; у 20 заголовка нет, в том числе четыре могут быть служебными. Наличие идентификатора само по себе не устанавливает автора, а равенство `connectorMid` идентификатору Wazzup ещё не проверено.

На всех 26 сообщениях, сопоставленных между `imopenlines.session.history.get` и `im.dialog.messages.get` по паре ID чата и ID сообщения, `author_id` второго метода совпал с `senderid` первого. Поэтому второй метод в этой сделке не дал независимой информации об авторе. В истории сообщений и их `params` не обнаружены проверенные структурные поля `direction`, `isEcho` или `fromMe`.

В двух других сделках, где есть сессии с подтверждённой меткой Wazzup, изучены ещё 97 сообщений в шести сессиях, включая одну с неопределённым коннектором; `author_id` также совпадал с `senderid` во всех 89 сопоставленных сообщениях. Не все страницы проверялись, и эти примеры нельзя считать полной статистикой. Два контрольных примера ранее были отнесены к Wappi по названию коннектора, однако данная диагностика не подтвердила тип по его ID, поэтому их тип отмечен как неопределённый; на них не следует строить заключение о достоверности автора Wappi.

В базе обнаружены сохранённые ранее коммуникации с названиями каналов Wazzup у 701 разных сделок. Это исторические записи, а не число ошибок или ожидающих разбора сделок и не оценка текущего использования Wazzup.

## Источники надёжных признаков

1. У Wazzup пользовательский API v3 документирует события с `messageId`, `channelId`, `chatId`, `isEcho` и данными автора. Сопоставление `messageId` с `connectorMid`, полнота доставки исходящих и доступ к такому API в данном аккаунте не проверены. Вебхук сам по себе не обещает доставку старой истории. [Документация вебхуков Wazzup](https://wazzup24.ru/help/documentacion-api/webhooks-es/).
2. У партнёрского Wazzup API v2 документирован запрос выгрузки истории в CSV, но он требует партнёрскую авторизацию `client_access_token`; доступность и структура выгрузки для этого аккаунта не подтверждены. [Выгрузка сообщений Wazzup](https://wazzup24.ru/help/api/messages/), [варианты доступа](https://wazzup24.ru/help/api-ru/sposoby-podkljucheniya/).
3. Wappi документирует получение истории по чату с полями `fromMe`, `id` и `chatId`. Для проверки нужно подтвердить доступ и сопоставимость идентификаторов; запросы не должны отмечать переписку прочитанной или запускать фоновую загрузку истории. [Документация Wappi](https://wappi.pro/api-documentation).

На этом этапе API вебхуки или подписки не менялись, к Wazzup/Wappi запросы с токеном не отправлялись. В локальных настройках токены под именами Wazzup/Wappi не обнаружены; существование доступа в другом месте не исключено. При попытке открыть кабинет Wazzup во встроенном браузере соединение завершилось таймаутом; это не подтверждает ни отсутствие аккаунта, ни состояние сервиса в целом.

## Дальнейшая проверка

Проверить наличие доступа к кабинету или API Wazzup/Wappi и сопоставить минимальный образец с историей Битрикса: внешние ID, направление, источник, время и вложения. Установить уникальность и полноту сопоставления отдельно для разных каналов и старых/новых сообщений. Только после подтверждения на исходных сообщениях можно использовать направление как основание вердикта. Для непокрытых случаев нужен процесс ручного подтверждения и безопасного повтора; сейчас он не реализован.

Автоматическая обработка, комментарии в CRM и уведомления в проверке не включались. После диагностики приложение оставлено в режиме настройки, удаление временного ключа проверено. Метод Битрикса `im.dialog.messages.get` документирован как получение истории; прямого обещания о неизменности статуса прочтения на его странице нет. Отдельные методы изменения прочитанности не вызывались. [История диалога Битрикс24](https://apidocs.bitrix24.ru/api-reference/chats/messages/im-dialog-messages-get.html).

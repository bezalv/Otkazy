# Защита идентичности сообщений — проект

Рабочая база не менялась. В таблице действует уникальность по `(deal_id, event_type, event_id)`, поэтому одна коммуникация может сохраниться дважды при переходе от `chat_<chat>_<message>` к `<session>_<message>`. Строка `lost_deals` при записи нового приложения сериализует его собственные обновления одной сделки, но не защищает от старого n8n или другого независимого писателя.

Подготовлен отдельный **неподключённый к автоматическим миграциям** `20261108_chat_identity_guard.sql`. Частичный уникальный индекс не изменяет содержимое и не объединяет строки. На покрытых формах он не позволяет одновременно сохранить две строки с одинаковыми сделкой, чатом и числовым ID сообщения. Конкурирующие вставки всех писателей PostgreSQL проверяются одним ограничением. Он может отклонить и два разных сообщения, если их ID повторяются между сессиями: свойство уникальности по чату пока не доказано. Отдельные файлы `file_*`, пропущенные chat_id и некорректные формы индексом не защищены. Попытка записи второй формы получает `23505`; старый n8n и текущий код не умеют автоматически разрешать этот конфликт.

Для ручной диагностики доступен `auditChatAliasCandidates` в `app/src/pilot/chat-alias-audit.mjs`: транзакция `REPEATABLE READ READ ONLY`, только одна сделка и чат, максимум 50 запрошенных ID и 200 найденных строк. Результаты `none`, `one_unverified_candidate`, `multiple_candidates` описывают только покрытые синтаксические формы из текущего снимка таблицы. Они **не подтверждают** ни идентичность, ни её отсутствие в других форматах, сделках или чатах, ни историческую полноту. Функция не меняет БД и не подключена к записи. Автоматических выводов о доставке и вердикте по её результату делать нельзя.

## Перед возможным внедрением

1. Выполнить только чтение `20261108_chat_identity_preflight.sql`, отдельно исследовать непокрытые форматы и все группы потенциальных совпадений. Совпадение тройки — кандидат, а не доказательство идентичности; существующие строки не менять и не удалять автоматически.
2. Подтвердить контракт ID и доступную полноту исторических сессий. Проверить наличие других писателей и то, что `chat_id` у них достоверен. Оценить стоимость построения индекса и права на БД.
3. Реализовать производителя подтверждения для `chatEventCandidates`: связь `session ↔ chat ↔ deal`, точный снимок сообщения, а также однозначность ID в полном доступном наборе сессий. Одно чтение текущей сессии этого не доказывает. Для неподтверждённых случаев обеспечить явный статус и последующую проверку, а не угадывать.
4. В сохранении результата выполнять поиск кандидатов, выбор существующего ID и запись в одной транзакции. Сериализовать конкурирующие операции приложения по ключу сделки, чата и сообщения; повторять после `23505` лишь после отката и повторной проверки снимка, без повтора при неизвестном исходе COMMIT. Сохранить историю перезаписей и не трогать вложения.
5. Проверить на **настоящем изолированном PostgreSQL** две одновременные транзакции и внешнего писателя: при разных псевдонимах проходит не более одной вставки, вторая получает `23505`. Текущие тесты PGlite проверяют DDL и последовательные попытки, но не проверяют реальную конкуренцию, `CONCURRENTLY` и роль старого n8n.
6. Только после этих условий планировать отдельное развёртывание. `CREATE UNIQUE INDEX CONCURRENTLY` выполняется вне транзакции. При неудаче может остаться невалидный индекс: проверить `pg_index.indisvalid`, убрать такой индекс отдельным `DROP INDEX CONCURRENTLY`, устранить причину и повторить. Откат индекса не удаляет данные. До применения подтвердить мониторинг конфликтов и влияние на каждый действующий конвейер.

Пока первые четыре пункта не выполнены, индекс — защитный прототип, а не готовая миграция для рабочей базы.

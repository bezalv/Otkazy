# Промежуточное сохранение до судьи

Проект схемы `20261109_prejudge_artifacts.sql` **не применён** к рабочей базе. По умолчанию новый путь выключен; существующие setup и обработка остаются прежними. Для локальной проверки есть `tests/restore-persistence/prejudge.test.mjs` и `tests/restore-pipeline/prejudge-stage.test.mjs`.

При явном `persistInputsBeforeJudge: true` обработчик под действующей арендой и подтверждённым переходом сначала сохраняет ограниченную проекцию исходной переписки и сообщений. После завершения каждого звонка или голосового он сохраняет кандидат транскрипта, а перед судьёй — нормализованные коммуникации и пакет фактов. Обычные URL остаются; распознанные в них токены, подписи, учётные данные и секретный сегмент вебхука скрываются. Судья получает именно эту сохранённую версию, исходный пакет сохраняется только в виде SHA-256. Полнота распознавания произвольных секретов не гарантирована. Ошибка сохранения останавливает следующие вызовы транскрайбера и модели; отдельные запросы внутри уже запущенного транскрайбера пока не останавливаются при потере аренды. SQL не записывает комментарии, уведомления, вердикты или клиентские карточки Битрикса; новые строки изолированы от прежних таблиц приложения.

При дополнительной явно заданной `sttAttemptPolicy: { sha256, expectedEngine }` запись попытки идёт до отправки аудио в STT. В хеш политики необходимо включить проверенные версию STT, настройки сегментации и используемую модель; `expectedEngine` должен соответствовать фактическому серверу. STT повторно скачивает файл, считает SHA-256 его байтов и ищет готовый ответ того же источника, сделки, перехода, канальности, роли и политики. При совпадении платный POST не делается; при других байтах создаётся новая попытка. Потерявшая аренду попытка помечается `unknown`; на один ключ допускаются максимум две попытки. Неизвестная попытка могла быть оплачена: счётчик не является финансовым лимитом и не ограничивает число внутренних запросов самого STT.

Протокол опционален и в развернутом приложении не включён; без него прежняя защита по-прежнему переводит повтор в `needs_review`. При новом протоколе старые незавершённые прогоны без журнала не возобновляются автоматически; незавершённая отправка судье той же операции также требует проверки, но намеренный новый ручной прогон завершённой сделки поддерживается. Таблица попыток сама атомарно хранит готовый транскрипт, после чего он дополнительно попадает в общие материалы. Два результата разных фрагментов внутри **ещё не завершённого звонка** отдельно пока не сохраняются: для этого требуется изменение STT-сервиса. При пропаже ответа от последнего кусочка записи повтор может снова оплатить этот звонок в пределах двух попыток.

Первая версия допускает задания с ключом `bitrix24:deal-stage-history:<id>` и задания ожидания/ручного/ночного повтора, для которых тот же переход подтверждён в `lost_audio_wait` по сделке и дате; для ожидающих записей дополнительно проверяется точный scheduled key. Задания без подтверждённого ID перехода блокируются до платного вызова. Совместное включение с экспериментальным определением автора запрещено. Прежде чем включать, необходимо подтвердить схему и права серверной роли в тестовой БД, проверить конкурентность нескольких соединений, определить срок хранения и ручное восстановление, согласовать и зафиксировать политику распознавания, проверить лимит расходов ручного теста и отдельно протестировать реальный сценарий без записи в рабочие карточки/уведомлений. Обе таблицы содержат тексты коммуникаций: RLS включён, публичных политик и grants не создаётся; права в конкретном Supabase-проекте следует проверить отдельно.

# Отказы Б24 — правила для Claude Code

Язык проекта — русский. Детали бизнес-логики и стека — в BRIEFING.md, не дублировать здесь.

## n8n 2.12.3 — ограничения
- `process.env.X` и `$env.X` в Code-нодах **НЕ работают** (N8N_BLOCK_ENV_ACCESS_IN_NODE=true)
- `$env.X` работает только в expression-полях (URL, headers, body HTTP Request, Set, IF)
- В Code-нодах нет `fetch`/`axios`, но `await this.helpers.httpRequest({...})` работает и вовсю используется в проде («Обработать 1 сделку», `screenshots-fetch`). Запросы, которым нужен credential n8n (Polza, Supabase Postgres), всё равно делаем HTTP Request нодой — в Code-ноду креды не подставить.
- SplitInBatches v3: сбор результатов только через `$input.all()`
- Webhook ноды: webhookId должен совпадать с path, иначе молчаливый 404
- `n8n_autofix_workflow` ломает typeVersions — не использовать
- Set-ноды (typeVersion 3.4+) по умолчанию не пробрасывают поля входа. Если Set стоит в основном потоке перед Code-нодой которая ждёт body вебхука — обязательно включать `includeOtherFields=true` (Include Other Fields в UI), иначе входные данные теряются.

## Правки воркфлоу через MCP

- **Правка через `n8n_update_partial_workflow` сразу работает в проде.** Отдельной публикации нет и ждать её не надо: переключение на Sol пошло в живые разборы с 04:28 без каких-либо дополнительных действий. Не писать в отчётах «ждёт публикации» и не просить опубликовать.
- Отсюда порядок, и он обязателен:
  1. **До правки** — бэкап затрагиваемых нод в `tmp/backup/` **выгрузкой из n8n**, а не переносом кода руками: `node bench/dump-node.mjs --wf <id> --node "<имя>"` (или `--all` для всех Code-нод). Перенос руками на 12–20 КБ кода гарантированно вносит искажение.
  2. **До правки** — проверка логики на моках (`tests/`), а не на живых сделках.
  3. **После правки** — `n8n_validate_workflow` по каждому затронутому воркфлоу.
- Точка отката, кроме файлов: локальные снапшоты n8n-mcp пишутся **перед** изменением, поэтому нужная версия — та, что создана непосредственно перед правкой. Проверять диффом (`mode: "diff"`), а не по времени: `diff <до> → <после>` должен показать ровно те ноды, которые правились.
- `n8n_autofix_workflow` не использовать — ломает typeVersions.
- Скрипт выгрузки работает через `N8N_API_KEY` из `.env` (добавлен 30.09). У MCP-сервера свой ключ в его конфиге, скриптам он недоступен — это разные каналы доступа.
- Код, перенесённый в ноду через MCP-вызов руками, после правки сверять машинно: выгрузить ноду и сравнить с файлом-источником. Ручной перенос 10–20 КБ проходит чисто далеко не всегда.

## Запуск воркфлоу
- Только через `n8n_test_workflow` MCP, **НЕ** через curl/bash (песочница → 403)
- После запуска — **СТОП**, ждать подтверждения пользователя «закончилось»
- Не проверять статус execution самому — это делает пользователь

## Правило: после запуска воркфлоу — стоп

Когда Claude (в чате или CC) запускает воркфлоу через n8n_test_workflow — он НЕ проверяет статус выполнения сам. Никаких:
- n8n_executions list/get
- n8n_get_workflow для «убедиться что активно»
- повторных запусков «на всякий случай»
- попыток диагностики по сообщениям вроде "No response from n8n server" или таймаутам

"No response" от n8n MCP ≠ ошибка воркфлоу. Это таймаут на HTTP-ответ webhook (30 сек), а воркфлоу при этом работает в фоне.

**Единственный источник истины — Саня.** Он смотрит в n8n UI executions и говорит:
- «работает / закончилось / упало»
- какой статус
- что видит в логах, если ошибка

До его сообщения — молчим, ничего не трогаем, БД не дёргаем.

Исключение: Саня сам попросил «проверь execution» или «посмотри логи» — тогда да.

## Тихий режим прогона
- `lost-batch` принимает `"silent": true`: AI-комментарий в карточку Б24 не пишется, уведомления РОПам не уходят.
- Флаг идёт «Параметры запуска» → «Получить сделки из Bitrix» → «Обработать 1 сделку» → в теле запроса к `lost-analysis`. Там `notify-prepare` читает его из `$('Webhook Блок 3').first().json.body.silent` и возвращает `[]`. Перед записью комментария стоит IF «Тихий режим?».
- Использовать для тестов и перепрогонов. Без флага поведение прежнее.

## Чаты Открытых линий (Wazzup + Wappi)
- Wappi идёт через Открытые линии так же, как Wazzup: сессии по `crm.activity.list(PROVIDER_ID='IMOPENLINES_SESSION')` → `SESSION_ID` → `imopenlines.session.history.get(SESSION_ID)`. Отдельная ветка под коннектор не нужна.
- Сообщение служебное, только если в нём **нет файлов** и выполнено одно из двух: поле `senderid` есть и равно 0, а заголовка Wazzup «=== Исходящее/Входящее сообщение» нет; либо текст совпал с шаблоном из `systemPatterns`. Отсутствие `senderid` — это НЕ 0.
- Файлы (`params.FILE_ID` и поле `files` ответа истории) читать ДО проверки на служебность, иначе голосовые без подписи теряются: пустой текст раньше считался служебкой.
- Регулярка вырезания BB-кодов — `/\[\/?\w[\w= ]*\]/g`. Лишний пробел после `\/?` ломает вырезание `[USER=…]`.
- Шаблоны служебки продублированы в `agent-facts-assembler` и `b4.5 Comm Analytics` («Анализ сделки»). При правке списка менять во всех трёх местах.

## Детектор «разговора не было»

- Транскрипт приписывает клиенту любой голос на той стороне. Если ответил автоответчик оператора, виртуальный помощник или человек сказал только «алло», в фактах появлялась реплика `actor=client`, и судья считал это контактом с клиентом. На сделке 119215 из двух таких звонков (11 и 6 сек) вышел вердикт «неправомерен, закрыли при доступном клиенте» и ложная ошибка «причина "не выходит на связь" не соответствует фактам».
- Одна функция `detectNoConversation`, продублирована в нодах `agent-facts-assembler` и `b4.5 Comm Analytics` (как `isAiComment`). Существующий `detectVoicemail` не заменён — новый детектор работает вторым слоем и добирает то, что тот пропускает: 468 звонков из 1595 коротких.
- **Источник правок — `prototype/lib/no-conversation.js`** (с комментариями и обоснованием каждого списка). Для вставки в ноды собирается компактная версия: `node bench/build-notalk-node.mjs` → `prototype/lib/no-conversation.node.js`, сборка сверяется с источником на восьми случаях. Править надо в источнике, иначе разъедется, как когда-то промпты v1.
- Пороги и списки фраз — константами сверху: `NOTALK_MAX_SEC` (20), `NOTALK_ZERO_SEC_CHARS` (200), `NOTALK_MEANINGFUL_CHARS` (12), `NOTALK_MANAGER_REST_CHARS` (15); списки `NOTALK_DIALING`, `NOTALK_MACHINE`, `NOTALK_BOT_SMALLTALK`, `NOTALK_MACHINE_IN_MANAGER`, `NOTALK_MANAGER_SYSTEM`, `NOTALK_BAD_LINE`, `NOTALK_NOT_CLIENT`, `NOTALK_GREETING`, `NOTALK_DEBRIS`, `NOTALK_PURPOSE`.
- Четыре причины: `machine` (автоответчик, голосовой помощник, бот-секретарь), `greeting_only` (прозвучало только приветствие, цель звонка не названа), `not_client` (трубку снял не клиент), `bad_line` (менеджер сам говорит, что связь не установилась).
- Главный принцип: **живые слова клиента важнее машинного признака.** Если после вырезания машинных фраз, приветствий и обрывков остался осмысленный текст — разговор был, звонок не помечается, даже если робот дозвона говорил в начале записи.
- Записи двухканальные, стороны не путаются: сообщения оператора связи звучат до ответа абонента и слышны на канале менеджера, поэтому там ищутся только длинные фразы целиком. Моно-записи («Говорящий:», 296 из 4226 в базе) разбираются отдельно: стороны не разделены, поэтому метятся только если весь текст — фразы робота и приветствия.
- В фактах такой звонок даёт один факт `source=call_event`, `actor=system` с пояснением, почему разговора не было, и исходными репликами в кавычках для прозрачности. Репликой клиента они больше не становятся.
- **Транскрипта нет вообще — детектор не срабатывает (правка 01.10.2026).** Если оба канала пусты, анализировать нечего, и утверждать «прозвучало только приветствие» нельзя: мы не знаем, что было в записи. Такой звонок уходит сборщику фактов, и тот говорит «запись есть, но не распознана — содержание неизвестно» либо «записи нет». До правки 25 коротких звонков без текста метились `greeting_only` и шли судье как доказанное отсутствие разговора. На проверенных 4921 звонке цифры не изменились (941 из 1595 коротких): там пустых транскриптов нет вовсе.
- В `b4.5` такой звонок не попадает в `calls_meaningful`, `calls_last_successful*`, `last_contact*`, разрывы и инициативу, но остаётся в `calls_total` — попытка была, РОП должен её видеть. Число таких звонков — в метрике `calls_no_conversation`.
- Списки фраз составлены по фактическим транскриптам 1595 коротких звонков и по стоп-листу системы обзвона (`tasks/2026-09-30-robot-phrases.txt`, 564 фразы). Стоп-лист взят не целиком: боты-«секретари» имитируют людей, и две трети его фраз может сказать живой клиент. Разбор на группы — `bench/data/robot-phrases-groups.json`, скрипт `bench/classify-robot-phrases.mjs`.
- Моки — `tests/notalk/run.js` (48 проверок). Прогон по всей базе коротких звонков — `node bench/fetch-short-calls.mjs` и `node bench/test-no-conversation.mjs`.

## Порог данных в коде (п.10)

- **Источник правок — `prototype/lib/data-sufficiency.js`**, моки `tests/data-sufficiency/run.js` (56 проверок).
- В коде — только крайний случай, до вызова платной ноды. Судья не вызывается, если нет **ничего сразу**: ни содержательной реплики клиента (речь в звонке, сообщение от 20 знаков, распознанное голосовое, реплика со скриншота), ни содержательной записи менеджера в CRM (от 20 знаков, кроме наших же AI-разборов), ни подтверждённого фактами технического отказа.
- Основной порог остаётся **в промпте судьи**: там есть исключения, которые код не различит. Пример из выборки — сделка 125119, клиент ответил «Я уже купил окна» (16 знаков, короче порога), и это однозначный отказ.
- **Почему комментарий менеджера спасает от отсечки.** Правило без него отсекало 61 сделку из 581 за 60 дней, и в 9 случаях судья был прав, а код — нет: технические отказы с формулировками вне списка маркеров («технически **не** возможно», «монтажники отказали», «плохие перекрытия») и совершённые покупки у конкурента, зафиксированные только менеджером. С комментарием как основанием отсекается 24 сделки, и все 24 судья сам пометил «недостаточно_данных» — расхождений ноль.
- Цепочка: `pipeline-gate-ok?` → `data-sufficiency` → `data-enough?` → либо `agent-judge-call`, либо сразу `verdict-router` с готовым вердиктом «недостаточно_данных». Оттуда путь штатный: мимо писателя в `skip-writer`, комментарий по шаблону с перечислением, чего нет. Показатели — в `judge.data_sufficiency` (число реплик, самая длинная, число комментариев, найденный маркер отказа, пороги), в базу попадают внутри `ai_judge_json`.
- Список маркеров технического отказа заведомо неполный, и это нормально: он не единственное основание, потому что содержательный комментарий спасает сделку и без него.

## Полнота данных и блокировка вердикта (шаг Б)

Пункты 1–3 документа `otkazy-reshennoe-v-spin.md`, перенесено 01.10.2026. **Источник правок — `prototype/lib/pipeline-gate.js`**, моки `tests/pipeline-gate/run.js` (52 проверки), сверка кода в нодах — `node bench/check-gate-nodes.mjs`.

- **Отметки полноты.** «Обработать 1 сделку» ведёт карту `_sources` по четырём источникам API Битрикса: `calls`, `openlines`, `comments`, `tasks`. Пока источник не отмечен `complete: true`, он считается непрочитанным — молчание не доказательство полноты. Ошибка API повторяется трижды (`b24Retry`, паузы 2 и 4 с). Скриншотов в карте нет: их метаданные приходят внутри комментариев, а сбой распознавания скриншота — вторая ось.
- **Сбор неполный → без вердикта.** Проверка стоит **до** вызова `lost-analysis`, поэтому платные ноды не запускаются вовсе: сделка возвращается с `_status: 'error'` и `_error: «сбор неполный: <источники>»`, «Подготовить SQL» пишет строку с `pipeline_error`. Блокирует всегда, в том числе на последней попытке.
- **Главное правило блокировки по распознаванию: только `retryable`.** Пустой результат без ошибки — это тишина в записи, а не сбой, и вердикт он не держит (иначе каждая тихая запись стопорила бы разбор). Не блокируют также: m4a/wav голосовые (известное ограничение SpeechKit → «[голосовое сообщение, не распознано]»), звонки без записи, моно-записи после моно-прохода.
- **Гейт перед судьёй.** `agent-facts-assembler` → `pipeline-gate` → `pipeline-gate-ok?` → либо `agent-judge-call`, либо `pipeline-gate-output` → Respond. Гейт собирает сбои из трёх мест: ошибки транскрипции звонков из «Собрать итог» (`transcription_stats.errors`, теперь с полем `retryable`), сбои голосовых из тела вебхука (`voice_failures`), сбои скриншотов из `screenshot_stats`. Заблокированная сделка не тратит деньги на судью, не получает комментарий в карточку и не поднимает уведомление РОПам.
- **Третья попытка не держит сделку.** Флаг `last_attempt` идёт цепочкой «Параметры запуска» → «Получить сделки из Bitrix» → «Обработать 1 сделку» → тело запроса к `lost-analysis`, как `silent` и `screenshots`. При нём сбой распознавания вердикт уже не блокирует: разбор идёт, а нераспознанный звонок даёт факт `source=call_event`, `actor=system` — «Звонок N сек: запись есть, но не распознана — содержание неизвестно». Сбой сбора по API блокирует и здесь.
- **Промпт судьи v2.8:** такой звонок не считается ни молчанием клиента, ни контактом по существу, ни доказательством в чью-либо пользу; в пороге достаточности данных не идёт ни в плюс, ни в минус. Отличается от «записи нет» (обычный недозвон) и от «ответил автоответчик» (там известно, что контакта не было).
- **Ночной повтор — `dqwzTtYN5MqQxx6V` («Отказ: Ночной повтор сбоев»), сейчас ВЫКЛЮЧЕН.** Выключен 01.10.2026: он ходит с `silent: false`, а в очереди лежат сделки из перепрогона месячной давности — уведомления по ним отправлять не нужно. Перед включением ограничить выборку свежестью сделки (см. Project.md). Cron `0 4 * * *`, таймзона воркфлоу `Asia/Novosibirsk`. Берёт из вью `lost_pipeline_attention` до 20 сделок с `retry_eligible`, делит на две партии (обычные и те, у кого следующая попытка третья — им `last_attempt: true`) и шлёт в `lost-batch` с `silent: false`: это живые разборы. **Счётчик попыток — без новой колонки:** число строк `lost_deal_analyses` с `pipeline_error`, накопившихся после последнего успешного разбора (миграция `db/migrations/lost_004_pipeline_attention.sql`).
- **Где смотреть заблокированные:** `select * from lost_pipeline_attention order by last_attempt_at desc`. Поля: `pipeline_error`, `gate_kind` (`collect` / `recognition` / `other`), `failed_attempts`, `retry_eligible`, `next_is_last`.

## Надёжность транскрипции (`FHdtN0HGjVAbe9Ow`)

Пункт 4 документа `otkazy-reshennoe-v-spin.md`, перенесено 01.10.2026. Образец — копия СПИН «КП: Транскрипция звонка» (`1JigaLPeRINUzePO`), Ф7.1/Ф7.3/Ф7.5/Ф7.7.

- **Источник правок — `prototype/lib/stt-reliability.js`**, моки `tests/stt/run.js` (75 проверок). Функции вставлены в ноды по частям (каждой — только нужное), единой сборки `.node.js` нет; расхождение ловится сверкой `node bench/check-stt-nodes.mjs` после выгрузки нод.
- **Счётчик попыток.** «Повторить или таймаут» берёт `attempt` из `$input` — состояния предыдущей итерации. Раньше читал из «Подготовить поллинг», где `attempt` всегда 0: счётчик навсегда оставался 1, предел 60 попыток не наступал, и при зависании SpeechKit подворкфлоу ждал без конца. После 60 попыток — `stt-poll-again?` → `stt-timeout` с `retryable: true`.
- **Ошибка SpeechKit.** «Парсинг транскрипта» сначала смотрит `error` в ответе операции: раньше ошибка принималась за пустую запись. Отдаёт `success: false`, `retryable` и `channels_mismatch`.
- **Отказ по числу каналов.** «Audio has N channels, but M requested» → `retryable: false`, и «Транскрибировать все звонки» по этому признаку запускает моно-проход. Регулярка шире, чем в СПИН (`/channels?/i` + `/requested/i`, без «in specification»): формулировка у SpeechKit менялась, а незамеченный случай превратил бы моно-запись в сбой сделки. **Проверку ошибки и моно-проход разделять нельзя** — порознь каждая моно-запись станет ошибкой.
- **Создание задания.** До трёх попыток с паузами 5 и 10 с, только при 5xx, таймауте или обрыве. 400 падает сразу.
- **Опрос статуса.** У «Проверить статус» `onError=continueRegularOutput` и таймаут 30 с; `stt-poll-state` стирает временную ошибку и считает её в `poll_transient` в пределах тех же 60 попыток, задание не пересоздаётся. Условие «Готово?» — `done === true || !!error`.
- **Адрес записи.** «Config + Фильтр звонков» берёт запись и из `audio_files[*].url`, и из `audio_url` (`SETTINGS.RECORD_URL`). Раньше смотрел только в `audio_files`, и звонок с записью только в `audio_url` в транскрипцию не попадал вовсе.
- **Проверка скачивания.** `stt-download-valid` → `stt-download-ok?` → S3 либо `stt-download-failed`. Требуется HTTP 200 и файл не меньше `STT_MIN_AUDIO_BYTES` (1024 байта): меньше килобайта — это заголовок без данных или страница ошибки Битрикса под кодом 200. Иначе `success: false`, `retryable: true` и понятная причина с кодом и размером. У «Скачать аудио из Bitrix» включён `fullResponse` (без него нет `statusCode`) и таймаут 60 с. Размер берётся из буфера через `getBinaryDataBuffer`: поле `fileSize` в binary — строка вида «1.2 kB», сравнивать её с порогом нельзя. Отличие от образца: там `throw` валит подворкфлоу, здесь — ответ с причиной.
- Не переносили из образца СПИН: `kp-stt-safe-input` (allowlist хоста записи, нормализация имени файла) — безопасность, исключена по решению Сани.

## Моно-записи звонков («Говорящий:»)
- Транскрипция идёт двумя проходами: стерео (`channel_count=2`, каналы «Менеджер»/«Клиент»), а если стерео-проход вернул пустой диалог — моно (`channel_count=1`, `speaker_role='Говорящий'`). Моно-проход отдаёт одну дорожку речи без разделения сторон, и подворкфлоу кладёт её целиком в `transcript_manager_text`. В базе таких звонков 362, канал клиента пуст у всех 362, текст живой у 269.
- **Источник правок — `prototype/lib/mono-transcript.js`**, компактная сборка для нод — `mono-transcript.node.js`. Моки: `tests/mono/run.js` (51 проверка).
- «Транскрибировать все звонки» помечает результат `_transcript_mode` ('stereo' / 'mono') — проход там известен достоверно. «Собрать итог» переносит пометку на звонок; если пометки нет (старый результат), режим определяется по «Говорящий:» в тексте.
- Сборщик фактов делает из моно-записи **один** факт `source=call_transcript`, `actor=unknown`, префиксы «Говорящий:» снимаются, в начале content — пометка «Запись без разделения сторон». Фактов `actor=manager` и `actor=client` такой звонок больше не даёт. Детектор «разговора не было» отрабатывает раньше, поэтому моно-записи с одним роботом сюда не доходят.
- В `b4.5` моно-звонок с живым текстом остаётся содержательным (`calls_meaningful`, `last_contact`) — контакт был, длительность настоящая. В инициативе он участвует наравне со стерео: направление звонка берётся из активности Битрикса и от режима транскрипции не зависит. Исключать его оттуда пробовали — откатили 01.10.2026, это теряло достоверные данные по 362 звонкам. Число таких звонков — `calls_mono_recorded`.
- В промпте судьи: `actor=unknown` нельзя приписывать ни клиенту, ни менеджеру, годится только как факт, что разговор состоялся, и как контекст. Proof Validator в `agent-judge-parse` на `client_statement`/`manager_statement` со ссылкой на такой факт даёт **предупреждение**, а не ошибку (`errorCount` не растёт): пруф слабый, но не выдуманный.

## Голосовые из чатов
- **Один факт на сообщение (правка 02.10.2026, п.8).** Пакет вклеивает расшифровку в текст сообщения, поэтому сборщик делает ОДИН факт: `chat_voice_transcript`, если в сообщении было голосовое (`transcript` непустой или `_has_audio_transcript`), иначе `chat`. Раньше из одного сообщения выходили два факта — `chat` с вклеенным текстом и `chat_voice_transcript` с той же расшифровкой под префиксом роли; за 60 дней дублями оказались все 28 голосовых фактов в 6 разборах, лишних 7 899 знаков. Журнал тоже печатал расшифровку второй раз блоком «--- Транскрипт голосового ---» — блок убран, статистика `has_voice_transcript` осталась.
- Имя файла голосового (`<хеш>.ogg` первой строкой) вырезается и из факта, и из журнала: судье это внутренний идентификатор, а читается как часть сообщения. Регулярка требует шестнадцатеричное имя от 8 знаков и перевод строки, поэтому обычный текст вроде «Окна.ogg это опечатка» не режется.
- **Источник правок — `prototype/lib/chat-voice.js`**, моки `tests/chat-voice/run.js` (36 проверок).
- Путь: `disk.file.get` → `DOWNLOAD_URL` → `lost-transcription`, `channel_count=1`.
- Кодировка в SpeechKit выбирается по расширению `file_name`, а не по типу файла: ogg/oga/opus → `OGG_OPUS` **без** `audioChannelCount`, mp3/mpga → `MP3` с `audioChannelCount`. Раньше `MP3` был захардкожен, и ogg отбивался с HTTP 400.
- m4a и wav SpeechKit v2 не поддерживает — в распознавание не отправляем.
- Нераспознанное или неподдерживаемое голосовое остаётся в журнале текстом «[голосовое сообщение, не распознано]» с ролью автора, а не выкидывается.

## Принцип минимальных правок схемы
При клонировании проекта (например, Отказы из Приостановленных) БД-схему клонируем 1:1. Добавляем только новые поля специфичные для нового проекта. Существующие поля НЕ переименовываем, даже если имя не идеально подходит — переименование требует синхронной правки кода воркфлоу и резко повышает риск несовпадений. Мёртвые поля оставляем пустыми.

## Модели LLM для мульти-агентного анализа
- **Judge и Writer работают на GPT-6 Sol (`openai/gpt-6-sol` через Polza), переключение 30.09.2026.** Разбор стоит ~3,6 ₽ за сделку против ~23,4 ₽ у Opus 4.7. Точка отката на Opus — `tmp/backup/tochka-otkata-2026-09-30.md` и `node bench/switch-model.mjs --rollback`.
- Параметры вызова обязательны и заданы в Code-нодах (`agent-facts-assembler` для судьи, `agent-judge-parse` для писателя), а не в HTTP-нодах: `provider.order = ["openai/flex","openai"]` с `allow_fallbacks: true`, `reasoning.effort = "low"`, `max_tokens: 16000`, у судьи ещё `response_format` со strict-схемой. Без `provider` Polza шлёт запрос обычному openai — в 2,1–2,5 раза дороже.
- Кто ответил, по ответу не видно: поле `provider` у Polza всегда `openrouter`. Запасного провайдера ловим по цене — `cost_rub` выше «токены × цена flex» более чем в 1,6 раза. Цены flex в `bench/prices.json`.
- Opus 4.7 до переключения: `anthropic/claude-opus-4.7`, лимиты 4000 у судьи и 2500 у писателя. Sonnet 3.7 давал заметно хуже: путал пол менеджера, вставлял запрещённые "если-то" скрипты, менее глубокий анализ.
- Константы моделей в prototype/lib/models.js.
- **Рабочие промпты: судья — `prototype/prompts/models/gpt-6-sol/judge.md`, писатель — `prototype/prompts/writer_v2.5.md`.** Промпт судьи под Sol собирается патчами из рабочего `judge_v2.7.md`: `node bench/build-prompt.mjs --model gpt-6-sol`. Патчи и причина каждого — в `prototype/prompts/models/gpt-6-sol/patches.json`; помеченные `enabled: false` в сборку не идут. Рабочий промпт (`judge_v2.7.md`) остаётся источником и правится отдельно.
- Метка версии правил — `v2.7-sol`, пишется в `prompt_version` из двух мест BhPWB9S6W5dlMUvV. Разборы до и после перехода надёжнее различать по `judge_model`.
- Источник истины всё равно нода в n8n: правишь промпт — обнови и файлы, иначе разъедутся, как когда-то разъехались v1.
- Стенд для проверки модели на сохранённых входах — `bench/`, описание в `bench/README.md`. Потолок расходов задан в `bench/run.mjs`.

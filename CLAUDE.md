# Отказы Б24 — правила для Claude Code

Язык проекта — русский. Детали бизнес-логики и стека — в BRIEFING.md, не дублировать здесь.

## n8n 2.12.3 — ограничения
- `process.env.X` и `$env.X` в Code-нодах **НЕ работают** (N8N_BLOCK_ENV_ACCESS_IN_NODE=true)
- `$env.X` работает только в expression-полях (URL, headers, body HTTP Request, Set, IF)
- Code-ноды не ходят в сеть — HTTP только через HTTP Request ноды
- SplitInBatches v3: сбор результатов только через `$input.all()`
- Webhook ноды: webhookId должен совпадать с path, иначе молчаливый 404
- `n8n_autofix_workflow` ломает typeVersions — не использовать
- Set-ноды (typeVersion 3.4+) по умолчанию не пробрасывают поля входа. Если Set стоит в основном потоке перед Code-нодой которая ждёт body вебхука — обязательно включать `includeOtherFields=true` (Include Other Fields в UI), иначе входные данные теряются.

## Запуск воркфлоу
- Только через `n8n_test_workflow` MCP, **НЕ** через curl/bash (песочница → 403)
- После запуска — **СТОП**, ждать подтверждения пользователя «закончилось»
- Не проверять статус execution самому — это делает пользователь

## Правило: после запуска воркфлоу — стоп

Когда Claude (в чате или CC) запускает воркфлоу через n8n_test_workflow — он НЕ проверяет статус выполнения сам. Никаких:
- n8n_executions list/get
- n8n_get_workflow для «убедиться что активно»
- повторных запусков «на всякий случай»
- попыток диагностики по сообщениям вроде "No response from n8n server" или таймаутам

"No response" от n8n MCP ≠ ошибка воркфлоу. Это таймаут на HTTP-ответ webhook (30 сек), а воркфлоу при этом работает в фоне.

**Единственный источник истины — Саня.** Он смотрит в n8n UI executions и говорит:
- «работает / закончилось / упало»
- какой статус
- что видит в логах, если ошибка

До его сообщения — молчим, ничего не трогаем, БД не дёргаем.

Исключение: Саня сам попросил «проверь execution» или «посмотри логи» — тогда да.

## Тихий режим прогона
- `lost-batch` принимает `"silent": true`: AI-комментарий в карточку Б24 не пишется, уведомления РОПам не уходят.
- Флаг идёт «Параметры запуска» → «Получить сделки из Bitrix» → «Обработать 1 сделку» → в теле запроса к `lost-analysis`. Там `notify-prepare` читает его из `$('Webhook Блок 3').first().json.body.silent` и возвращает `[]`. Перед записью комментария стоит IF «Тихий режим?».
- Использовать для тестов и перепрогонов. Без флага поведение прежнее.

## Чаты Открытых линий (Wazzup + Wappi)
- Wappi идёт через Открытые линии так же, как Wazzup: сессии по `crm.activity.list(PROVIDER_ID='IMOPENLINES_SESSION')` → `SESSION_ID` → `imopenlines.session.history.get(SESSION_ID)`. Отдельная ветка под коннектор не нужна.
- Сообщение служебное, только если в нём **нет файлов** и выполнено одно из двух: поле `senderid` есть и равно 0, а заголовка Wazzup «=== Исходящее/Входящее сообщение» нет; либо текст совпал с шаблоном из `systemPatterns`. Отсутствие `senderid` — это НЕ 0.
- Файлы (`params.FILE_ID` и поле `files` ответа истории) читать ДО проверки на служебность, иначе голосовые без подписи теряются: пустой текст раньше считался служебкой.
- Регулярка вырезания BB-кодов — `/\[\/?\w[\w= ]*\]/g`. Лишний пробел после `\/?` ломает вырезание `[USER=…]`.
- Шаблоны служебки продублированы в `agent-facts-assembler` и `b4.5 Comm Analytics` («Анализ сделки»). При правке списка менять во всех трёх местах.

## Голосовые из чатов
- Путь: `disk.file.get` → `DOWNLOAD_URL` → `lost-transcription`, `channel_count=1`.
- Кодировка в SpeechKit выбирается по расширению `file_name`, а не по типу файла: ogg/oga/opus → `OGG_OPUS` **без** `audioChannelCount`, mp3/mpga → `MP3` с `audioChannelCount`. Раньше `MP3` был захардкожен, и ogg отбивался с HTTP 400.
- m4a и wav SpeechKit v2 не поддерживает — в распознавание не отправляем.
- Нераспознанное или неподдерживаемое голосовое остаётся в журнале текстом «[голосовое сообщение, не распознано]» с ролью автора, а не выкидывается.

## Принцип минимальных правок схемы
При клонировании проекта (например, Отказы из Приостановленных) БД-схему клонируем 1:1. Добавляем только новые поля специфичные для нового проекта. Существующие поля НЕ переименовываем, даже если имя не идеально подходит — переименование требует синхронной правки кода воркфлоу и резко повышает риск несовпадений. Мёртвые поля оставляем пустыми.

## Секреты
- `service_role_key` и `db_password` — **никогда в чат**, только в `.env` или credentials n8n
- Утечка секрета → немедленная ротация

## Webhook paths
- Префикс `lost-*` обязателен (lost-trigger, lost-batch, lost-transcription, lost-analysis)
- НЕ `reactivation-*` — это проект Приостановленных

## Bitrix24
- Для методов `im.*` (уведомления, сообщения — например `im.notify.system.add`) входящему вебхуку нужен scope «Чат и уведомления (im)». Без него вызов падает с `insufficient_scope`.
